# netclip

两台 Windows 电脑之间**共享鼠标键盘 + 同步剪贴板**（含 Office / MathType 私有格式保真）的自用工具。

目标是替代 Mouse Without Borders 和 Deskflow 在当前使用中暴露的三个问题：

| 现有工具的问题 | netclip 的做法 |
|---|---|
| MWB 会让其它应用无法写入剪贴板 | 用 `AddClipboardFormatListener` 而非 view 链；读/写剪贴板都是**毫秒级临界区**；抢不到锁按退避重试，失败就放弃这一次，绝不长时间占用 |
| MWB 会卡住 | 钩子回调只入队不判断；网络/路由/钩子/看门狗各跑独立线程；任何一条线程都不阻塞在另一条上 |
| Deskflow 不能传文件 | 三通道 TCP（input / clip / file）；文件走独立通道，传完在接收端用 `CF_HDROP` 落盘并放进剪贴板，对端粘贴就是本地文件 |

## 快速开始

### 方式一：双击 `start.bat`（推荐）

双击 `start.bat` 会出现一个中文菜单：

```
  1) 启动 netclip（后台运行，用右下角托盘图标控制）
  2) 启动并显示日志窗口（排查问题用）
  3) 只校验配置，不启动
  4) 运行自检（连通性 / 剪贴板 / 文件 / 托盘）
  5) 打开 config.toml
  6) 打开日志文件
  7) 开机自动启动：安装 / 卸载
  0) 退出
```

它会自己找 Python、检查配置（没有 `config.toml` 就从示例生成并打开记事本让你改）、
并给出中文错误提示。**日常使用就选 1**：后台运行，没有控制台窗口，
所有操作走右下角托盘图标（右键菜单可以暂停共享、把光标拉回本机、打开日志、退出）。

> `start.bat` 本身是**纯英文 ASCII** 的，一行中文都不输出。原因写在文件注释里：
> cmd.exe 按系统 ANSI 代码页逐字节读 `.bat`，中文注释在这种解释方式下会被撕裂，
> 碎片甚至会被当成命令执行。所有中文提示都放在 `start.ps1` 里（带 UTF-8 BOM）。

### 方式二：命令行

```powershell
cd netclip
Copy-Item config.example.toml config.toml
```

在两台机器上分别编辑 `config.toml`，至少改这三处：

```toml
[device]
name = "desktop-a"          # 两台机器填不同的名字

[network]
peer_ip = "192.168.1.42"    # ★ 填对方的 IP（A 填 B 的，B 填 A 的）

[layout]
peer_position = "right"     # ★ 对端在本机的哪一侧：right/left/up/down

[security]
psk = "换成一个随机字符串"    # 两台必须完全一致
```

然后：

```powershell
python -m netclip --check          # 先校验配置，打印几何预演
python -m netclip                  # 启动
```

没有依赖要装（Python 3.10+ 标准库 + 自带的 ctypes 绑定；`pywin32` 和 `pillow`
存在时会被用上，但**不是必需的**）。

## 命令行

```
python -m netclip [选项]

  --config PATH        配置文件（默认找程序目录的 config.toml）
  --check              只校验配置并打印解析结果
  --gen-config [PATH]  生成默认配置文件（--force 覆盖）
  --dump-formats       打印当前剪贴板的全部格式（诊断 Office/MathType）
  --seconds N          运行 N 秒后自动退出（冒烟测试用）
  --status-interval N  状态行打印间隔（0 = 不打印）
  --log-level LEVEL    覆盖日志级别
  --no-log-file        只输出到控制台
  --no-tray            禁用系统托盘图标
  --port-offset N      所有端口整体偏移 N（同机跑两个实例联调用）
```

### 自检工具

```powershell
python -m netclip.selftest env               # 环境与依赖
python -m netclip.selftest clipboard         # 剪贴板往返（会自动还原）
python -m netclip.selftest clip-loop         # 剪贴板同步的本地环回（不需要第二台机器）
python -m netclip.selftest files-loop        # 文件同步的本地环回（造文件、传、逐字节比对）
python -m netclip.selftest tray --seconds 3  # 托盘图标（会真的出现一个图标，然后移除）
python -m netclip.selftest hooks --seconds 5 # 装真实钩子，观察事件与回调耗时
python -m netclip.selftest keys --seconds 8  # 打印每次按键的 vk / 扫描码（排查"某个键不对"）
python -m netclip.selftest loop --seconds 10 # 连通性：连上对端收发帧，但**不转发**输入（最安全）
python -m netclip.selftest warpguard         # 回声防护：确认自己挪光标不会被当成用户输入转发
python -m netclip.selftest inject            # 注入识别：确认自己的注入不会被当成真实输入
```

`loop` / `warpguard` / `inject` 这三个是**定向**排查工具，各针对一类具体的坏点，
比"整体不工作"这种描述有用得多：

| 自检 | 回答的问题 |
|---|---|
| `loop` | 两端到底能不能连上、帧能不能双向流动（不做任何转发，最安全） |
| `warpguard` | "鼠标被吸在一个位置高频抖动、推不动" —— 自己挪光标有没有产生被转发的移动事件 |
| `inject` | 注入的事件有没有被识别为"本机注入"（认不出来就会自伤死循环） |

`warpguard` 在无桌面会话 / RDP / 光标本来就在目标位置时会跳过计数断言并打印一行
说明 —— 那不是失败，三条"没有多余事件被上报"仍然有效。

**`keys` 是查"某个键在对端不对"的第一把手**，和剪贴板问题用 `--dump-formats`
是同一个思路：先看清本机钩子上报的是什么。两个值的分工要记住：

* `vk` 只用来**查表**（归一化左右修饰键、判断是不是扩展键）；
* **真正注入到对端的是 `scan`**（`win/inject.py` 用 `KEYEVENTF_SCANCODE` 注入
  物理扫描码，这样不受目标机键盘布局影响）。

所以典型故障是：钩子把左右 Shift 都报成 `vk=0x10`，区别只在 `scan`
（左 `0x2A` / 右 `0x36`）。`scan` 对，注入就对；`scan` 丢了才会退化成"右 Shift
变成了左 Shift"。

**但真机上抓到的比这更阴 —— `ext` 也可能是错的。** 实测：

```
左 Shift  vk=0xA0  scan=0x2A  ext=False
右 Shift  vk=0xA1  scan=0x36  ext=True     ← 系统给右 Shift 置了扩展标志
右 Ctrl   vk=0xA3  scan=0x1D  ext=True     ← 这个是对的
```

`ext` 就是"这个键按了 **E0 前缀**"。而 `E0 36` 在 PC/AT 规范里**没有对应的键**
（小键盘 `/` 是 `E0 35`，小键盘 Enter 是 `E0 1C`）—— 照原样注入，用户按右 Shift、
对端出来的是别的东西，现象就是"右 Shift 没被映射"。

所以注入层做了**归一化**（`inject.normalize_extended`），规则**只有一条减法**：

> 扫描码**没有** E0 版本时，扩展标志一定是错的，清掉；有 E0 版本就照来源给的标志走。

| 扫描码 | 结果 |
|---|---|
| `0x36` 右 Shift、`0x2A` 左 Shift —— 没有 E0 版本 | **清掉**扩展标志 |
| `0x35` 主键盘 `/`（非扩展）**和**小键盘 `/`（`E0 35`）共用 | 照标志走 |
| `0x1D` 左/右 Ctrl、`0x38` 左/右 Alt、方向键/小键盘数字 | 照标志走 |

**为什么不改钩子那一侧：** 钩子上报的是系统给的原样值，留着它有利于诊断
（`selftest keys` 要能看到这个反常的标志）。而"扫描码 + 扩展标志到底对应哪个键"
这件事，本来就属于注入层的职责。

#### 一次"做加法"的教训

第一版归一化里加了一条**加法**规则："有些扫描码没有非扩展含义，必须强制扩展"，
并把 `0x35` 也列了进去。结果 —— **`Shift+/` 打不出问号了**。

因为 `0x35` 非扩展就是**主键盘的 `/`**（`Shift+/` = `?`），扩展才是小键盘的 `/`。
强行加标志，主键盘 `/` 就被打成了小键盘的键。（`《》、"` 的键位不受影响，
所以只有问号消失，现象很迷惑。）

教训：**"某个扫描码的非扩展含义存不存在"不能靠猜。** 归一化只能做减法 ——
清掉确认非法的位，绝不主动补位。

**注意这个修复要两台都更新**：注入发生在**光标所在的那台**机器上，
所以"主机按右 Shift"这件事是主机在注入。

### 同一台机器上跑两个实例联调

不需要两台电脑也能验证网络层：用 `--port-offset` 错开端口，
两个实例都指向 `127.0.0.1`，一个加偏移一个不加。

```powershell
# 终端 1：正常端口
python -m netclip --config config-a.toml

# 终端 2：端口整体 +1000，peer_ip 指向 127.0.0.1
python -m netclip --config config-b.toml --port-offset 1000
```

### 开机自启

用 `start.bat` 的**第 9 项**（Windows 计划任务，登录时启动）。它会问你一个关键问题：
**是否以最高权限运行**。

- **是（推荐）**：登录时由系统直接提权启动，**不弹 UAC**，而且能控制任务管理器这类
  提权窗口（见下方「已知限制」第一条）。注册这一步本身需要管理员，所以要先走第 10 项。
- **否**：普通权限，任务管理器等提权窗口收不到转发的鼠标键盘。

也可以手动：

```powershell
$action  = New-ScheduledTaskAction -Execute "<pythonw.exe 路径>" -Argument "-m netclip" -WorkingDirectory "<项目目录>"
$trigger = New-ScheduledTaskTrigger -AtLogOn -User $env:USERNAME
$set     = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -StartWhenAvailable
Register-ScheduledTask -TaskName netclip -Action $action -Trigger $trigger -Settings $set -RunLevel Highest
```

`-RunLevel Highest` 就是"最高权限"。去掉它则是普通权限。

卸载：`Unregister-ScheduledTask -TaskName netclip -Confirm:$false`

> 用 `pythonw.exe` 而不是 `python.exe`，否则每次登录都会弹一个黑窗口。

#### 手动加计划任务：用 `netclip_task.vbs`

想自己在「任务计划程序」里配，用仓库根目录的 **`netclip_task.vbs`**：

| 选项卡 | 设置 |
|---|---|
| 常规 | **只在用户登录时运行** ；勾选 **使用最高权限运行** |
| 触发器 | 登录时（建议加 30 秒延迟） |
| 操作 | 程序 `wscript.exe`，参数 `"C:\...\netclip\netclip_task.vbs"`，起始于项目目录 |

它做两件事：调 `start.ps1 -Run`（非交互启动），失败时弹一个消息框告诉你去看日志。

**为什么是 `.vbs` 而不是 `.bat` / `.ps1`：** `start.bat` 会闪一下控制台窗口，
`powershell.exe -WindowStyle Hidden` 也会闪。只有 `wscript.exe` 能把子进程的窗口
样式设成 0，**完全不出现任何窗口**。

**为什么这个 `.vbs` 是纯 ASCII：** `wscript.exe` 读没有 BOM 的 `.vbs` 用的是
**系统 ANSI 代码页**（中文机器上是 GBK），写中文会变乱码 —— 和 `.ps1` 遇到的
是同一类坑，但 `.vbs` 没有 BOM 这种约定可用。它又是**开机自启**的脚本，
乱码导致语法错误的话没人看得见。所以中文全在 `start.ps1` 里，这个文件只有英文。

> **绝对不要选"不管用户是否登录都要运行"。** netclip 需要**交互式桌面会话**：
> 低级钩子、`SendInput`、剪贴板在 session 0 里全部静默失效。

`start.ps1 -Run` 的行为：停掉已有实例（**包括以管理员身份运行的** —— 普通权限的
控制台连它的命令行都读不到，所以这里靠监听端口反查 PID），然后后台拉起
`pythonw.exe -m netclip`。全程不问任何问题，用退出码报告结果 —— 隐藏窗口下
`Read-Host` 会让任务**永远挂着**，表现就是"任务在跑，但 netclip 根本没起来"。

## 双机验收清单

按顺序做，每步确认后再进行下一步。**不要跳过前面的步骤直接测鼠标共享** ——
出问题时会分不清是网络、钩子还是几何的问题。

1. **连通性**
   ```powershell
   # 两台都跑，观察是否三通道都连通
   python -m netclip.selftest loop --seconds 10
   ```
   期望：`input / clip / file 通道已连通`，并且"收到对端帧"计数增长。

2. **钩子**
   ```powershell
   python -m netclip.selftest hooks --seconds 5
   ```
   期望：移动鼠标/敲键盘时计数增长，回调峰值远小于 5000us。

3. **鼠标跨屏**（先只开鼠标）
   ```toml
   [input]
   share_keyboard = false
   ```
   启动后把光标推到配置的那条边。期望：光标出现在对端对应边缘，
   能正常移动和点击；从对端朝本机的边缘推回来能回来。

4. **键盘**
   打开 `share_keyboard = true`。期望：对端能正常打字；
   `Ctrl+Alt+Home` 能随时把光标拉回本机；`Ctrl+Alt+Pause` 能暂停/恢复共享。

5. **断线保护**
   光标推到对端后把网线拔掉 / 关掉对端进程。期望：**6 秒内**光标自动回到本机，
   并且不会出现"本机点击变成 Ctrl+点击"（残留按键会被释放）。

6. **剪贴板**
   文本 / 图片 / HTML。然后测 Office 与 MathType：
   ```powershell
   # 复制后立刻在两台机器上各跑一次，对比格式清单
   python -m netclip --dump-formats
   ```

7. **文件同步**
   在资源管理器里复制几个文件（含中文名、一个大文件），到对端资源管理器 `Ctrl+V`。
   期望：文件出现在暂存目录，粘贴出来的是**本地文件**（不是快捷方式也不是错误）。
   暂存目录位置：
   ```powershell
   echo $env:LOCALAPPDATA\netclip\staging
   ```

   先用 `python -m netclip.selftest files-loop` 单独确认这一侧的逻辑没问题。

## 配置说明

`config.example.toml` 里有逐行的中文注释。几个关键项：

### 摆放关系（决定鼠标从哪条边进出）

```toml
[layout]
peer_position = "right"   # ★ 对端在**本机**的哪一侧
alignment = "center"      # 两边屏幕尺寸不同时，沿共享边的对齐方式
edge_band_px = 2          # 边缘判定带宽
warp_inset_px = 8         # 穿越后本机光标内缩，防弹跳
lock_mouse_on_drag = true # 按住鼠标键时不切屏（防止把窗口"甩"到对端）
```

> **★ 两台机器必须填相反的值。** 这个键问的是"**对端**在我哪一侧"，
> 而两台机器互为对方的对端，所以合法组合只有四种：
>
> | 主机填 | 从机必须填 |
> |---|---|
> | `right` | `left` |
> | `left`  | `right` |
> | `up`    | `down` |
> | `down`  | `up` |
>
> 两边填成一样是很自然的误解（"两台机器的摆放关系"听起来像共享设置），
> 但后果很难从现象上认出来：对端会把光标摆到自己**反方向**的那条边上，
> 离主机模型差整整一个屏宽，从机光标从第一帧起就贴在错误的边缘、
> 只能单向挪几像素然后被拉回来 —— 也就是用户说的"鼠标像被弹簧拉住"。
> netclip 在握手时会交换这个字段，发现组合不是相反就**直接报 ERROR**。

`alignment` 只影响"两边屏幕沿共享边的尺寸不同"的情况。例如本机 1440 高、
对端 1080 高、居中对齐时，只有中间 1080 像素的高度能穿过去；对端上下各留
180 像素的"死角"。

### 文件同步阈值

```toml
[clipboard.files]
auto_transfer_max_mb = 200        # ★ 阈值
over_threshold_action = "ask"     # 超过阈值时: ask / skip / transfer
```

- `≤ 阈值`：直接流式传到对端，落盘后放进剪贴板（对方粘贴就是本地文件）
- `> 阈值`：按 `over_threshold_action` 处理（默认弹提示问是否同步）

### 剪贴板格式（Office / MathType 保真的关键）

```toml
[clipboard.formats]
forward_all = true        # 全格式转发：PPT 形状、MathType 公式才能保持"可编辑"
per_format_max_mb = 100   # 单个格式上限，超了只丢这一个格式，其它继续同步
compress = true
inline_html_refs = true   # HTML 里的 file:/// 图片内联成 data URI
```

**重要前提**：保真需要**两端都装对应软件**。
- PPT 形状要可编辑 → 两端都要有兼容版本的 PowerPoint
- MathType 公式要可编辑 → 两端都要装 MathType
- 对端没装对应软件时，会自动降级成图片/文本（并且会提示）

## 设计决策记录

### 为什么用 TCP 而不是 UDP

- 键盘、鼠标按键、剪贴板、文件这四类都要求**可靠 + 有序 + 不重复**，只有鼠标
  移动是可以丢的。用 UDP 意味着要自己实现序列号、重传、去重、拥塞控制 ——
  等于写一个更差的 TCP。
- 担心的"传大文件时鼠标卡顿"是**共享一条流**的问题，不是协议的问题。解法是
  三通道隔离 + 移动事件合并，TCP 就能彻底解决。
- 移动事件用增量 `(dx, dy)` 发送并**累加合并**：丢的是中间采样点，位移总量不丢，
  既不堆积延迟也不产生漂移。

### 为什么拆三条 TCP 连接

鼠标移动是"低延迟、可丢弃"的，文件是"高带宽、不可丢弃"的。同一条 TCP 流上传
大文件时，文件字节会排在鼠标事件前面，鼠标就会卡。拆开后互不影响。

三条连接都是双向复用的，双方都能拨号也能接受。两侧同时拨号会产生交叉连接，
处理方式是让"主动拨号方"赢（入站连接等 350ms 再决定是否拒绝）。

### 线程模型

```
主线程        轻量 PeekMessage 循环（响应退出；将来承载托盘）
网络线程      asyncio：三通道收发、握手、心跳、重连；收到对端输入直接注入
钩子线程      WH_MOUSE_LL / WH_KEYBOARD_LL + 自己的消息循环
路由线程      消费钩子事件，跑 LOCAL/REMOTE 状态机
看门狗线程    断线回拉、松键、钩子自愈
```

**网络线程是 asyncio 事件循环的 owner，所以它自己负责 `NetManager.stop()` 和
`loop.close()`。** 早期版本让主线程用 `run_coroutine_threadsafe` 去停网络，
结果和网络线程的 `loop.close()` 抢跑，稳定复现
`coroutine was never awaited` / `Event loop is closed`。

### 钩子回调的纪律

Windows 对低级钩子有 `LowLevelHooksTimeout`（默认 300ms）——回调超时会被**静默摘掉**，
表现是"鼠标突然全部失灵但程序还在跑"，且没有任何报错。

所以钩子回调里只做：读结构体字段 → 整数比较 → 原地赋值到复用的 `InputEvent`
→ 入队。**不分配对象、不记日志、不碰网络、不碰锁、不碰剪贴板。**

"是否吞掉这个事件"也只看一个原子布尔量（`_swallow`），真正的判断逻辑在路由线程里。

### 剪贴板：`RegisterClipboardFormatW` 的坑

标准格式必须**查表**拿格式号，不能靠 `RegisterClipboardFormatW("CF_UNICODETEXT")`
反推 —— 后者会返回一个运行期分配的 ID（实测 49273），而不是 13。

这个错误非常隐蔽：数据确实写进了剪贴板，但别的程序按 `CF_UNICODETEXT(13)` 去找
时找不到，表现就是"复制了但粘贴是空的"。见 `win/clipboard.py` 里的
`_STANDARD_BY_NAME` 和 `format_id_for()`。

私有格式则相反：格式号是运行期分配的，两台机器上可能不同，但**名字是稳定的**。
所以协议里一律传格式名字符串，对端重新注册。

### 剪贴板数据长度：`GlobalSize` 的取整

`GlobalSize()` 返回的是**分配大小**（Windows 按 256 字节向上取整），不是数据长度。
所以自己 `GlobalAlloc` 出来的剪贴板数据回读时会多出尾部填充。

怎么剔除，取决于格式是不是自描述的（见 `clipboard.py` 的 `_LENGTH_RULE`）：

| 规则 | 适用格式 | 做法 |
|---|---|---|
| `terminated` | `CF_UNICODETEXT` / `CF_TEXT` / `CF_OEMTEXT` | 找第一个偶对齐的 `\0\0`（或 `\0`）终止符 |
| `self` | `CF_HDROP` / `CF_DIB` / `CF_DIBV5` / `CF_ENHMETAFILE` / `CF_METAFILEPICT` / `CF_WAVE` / `CF_TIFF` … | **绝不裁剪**，按各自长度字段精确切分 |
| `zeros` | 不认识的注册格式（默认） | 去掉尾部零字节 |

**为什么 `self` 类绝不能裁剪尾部零**：那是真实数据。`CF_HDROP` 最典型 ——
它的路径列表以 `\0\0` 结尾，裁掉之后最后一个文件名会少一个字符，
而且**不报任何错**。

### 等价表示去重：不能只看格式名

Windows 经常同时提供同一份内容的多种表示（写 `CF_UNICODETEXT` 时会顺带生成
`CF_TEXT` / `CF_OEMTEXT`）。全传过去没有意义，还会让对端程序挑到有损的那个。

但"按优先级只留第一个"是**错的**：`CF_DIBV5` 有时在格式表里存在、句柄却是空的
（写入方没真的提供数据），如果按名字提前把 `CF_DIB` 跳过了，结果就是整张图都没同步。

正确做法在 `clipboard.capture(dedupe_groups=True)`：**按优先级依次尝试读取，
只保留第一个真正读出来的**。

### 剪贴板同步的决策与回退

`clipsync/policy.py` 把"要不要传、传哪些"从 I/O 里拆出来，策略可单独测试，
出问题时 `SyncDecision.reason` 能直接告诉用户为什么没同步。

三种结果：

* `full` —— 完整传输内容（能塞进一帧时）
* `announce` —— 只发格式清单和大小，不传内容（超过上限时），并提示用户
* `skip` —— 完全不动（类别关闭、全部被过滤、没有内容）

"超过上限就只通知"而不是分块硬传，是刻意的：几十 MB 的 DIB 传过去会长时间占用
带宽、影响鼠标延迟，而这种场景更适合让用户走文件通道或自己重传。

### 文件同步：为什么"传完不能删"

Windows 的 `CF_HDROP` 是**引用式**的 —— 剪贴板里只放路径字符串，资源管理器在你
粘贴的那一刻才去读文件。所以接收端必须：

1. 把文件真正落盘到暂存目录；
2. 用**本地真实路径**构造 `CF_HDROP`；
3. **让文件留够时间**（`clipboard.files.staging_ttl_min`，默认 120 分钟），
   传完就删会导致"粘贴时提示文件不存在"。

暂存目录结构 `<root>/<对端名>/<传输ID>/<文件名>`，按传输分目录是为了同名文件
不互相覆盖，也便于整目录按 TTL 清理。

### 文件复制：三个连环坑，缺一个就"粘贴不了"

跨机复制文件比复制文本麻烦得多，因为剪贴板里放的是**路径引用**。真机上依次踩到：

**① 带对端路径的 Shell 格式会把粘贴带偏。** 复制文件时剪贴板里除了 `CF_HDROP`
还有 `Shell IDList Array`（内部是**源机器**的绝对 PIDL），而 Explorer 按保真度挑格式，
它的优先级**高于** `CF_HDROP` —— 于是对端照着源机器的路径去找文件。
真机现象："复制文件到主机粘贴，提示在 temp 文件夹中找不到文件"。

**② 但 `CF_HDROP` 本身必须继续发。** 它是接收端判断"这是一次文件复制"的
**唯一信号**。一刀切把所有带路径格式都过滤掉之后，接收端不知道要保留文件，
剪贴板帧一到就把刚写好的文件剪贴板抹掉。
所以发送端过滤的是 `SHELL_PATH_FORMATS`（= `PATH_BEARING_FORMATS` 去掉
`CF_HDROP`/`FileDrop`），接收端才用完整的 `PATH_BEARING_FORMATS` 决定"哪些不写"。

**③ 顺序是"先文件帧、后剪贴板帧"。** 发送端日志：`开始发送 1 个文件` 在前、
`已发送剪贴板` 在后。于是接收端会在文件落地**之后**才跑 `_apply_remote`，
它重写剪贴板时必须把本地 `CF_HDROP` 一起带上（`_local_files` 记着落盘路径）。
真机现象："文件成功拉到临时目录，但是粘贴不了" —— 文件明明在，剪贴板里却没有。

判断一帧是不是文件复制，看**帧里有没有 `CF_HDROP`**；不是的话要把
`_local_files` 清空，免得一次普通文本复制带上过期的文件路径。

**④ 拖放簿记格式绝不能跨机转发。** 剪贴板里除了文件路径，还有一批只在
"源和目标处于**同一次拖放会话**"时才有意义的格式：`Preferred DropEffect`、
`DataObjectAttributes`、`AsyncFlag`、`DropDescription`、`UIDisplayed`…

把它们按原样转发过去，对端的资源管理器会把它们当成**自己那次拖放**的状态：

* `AsyncFlag` 被截断成 1 字节却按 DWORD 读 → Shell 以为这是一次异步传递，
  **转沙漏空等**，什么都不粘贴；
* `DropDescription` 是定长结构（含两个 `MAX_PATH` 宽字符串），截断后按完整长度
  读会**越界访问** → 资源管理器**崩溃重启**。

所以发送端与接收端都把它们挡掉（`SHELL_BOOKKEEPING_FORMATS`），
落地时只写一份干净的 `CF_HDROP` + `Preferred DropEffect=COPY`。

**⑤ 定长结构绝不能"去尾部零"。** `Preferred DropEffect` 是 4 字节 DWORD
（`DROPEFFECT_COPY`=1 → `01 00 00 00`）。默认的长度规则会把尾部零当填充删掉，
只留 `01` 一个字节；而 Explorer 按 4 字节读，多读的 3 字节取决于堆内存 ——
只要拼出来不是 1，Shell 就认为"这不是一次复制"。凡是定长结构都要列进
"绝不裁剪"的名单。

**⑥ 不要自己造 `Shell IDList Array`。** 一度怀疑"只写 CF_HDROP 粘贴不了"，
于是用本地 PIDL 重建了 `CIDA` 结构 —— 结果**资源管理器的粘贴直接崩掉重启**
（对照实验：加它之前只是"什么都不发生"，不崩）。`CIDA` 只要有一点偏差，
Shell 就会越界解析，[已知的崩溃案例](https://www.xyplorer.com/xyfc/viewtopic.php?p=238443)
不少。`CF_HDROP` 单独使用是有官方文档背书的做法：它就是"用来传递一组**已存在文件**
的位置"的标准格式。造 PIDL 时还有两个坑值得记下：父 PIDL 不能另外调
`ILCreateFromPathW(目录)` 得到（和文件 PIDL 的前缀对不上），更不能跨调用按字节
比对 PIDL（同一路径两次调用返回的字节都不同）。

排查这个问题的命令：`python -m netclip --dump-formats`，它会把文件类格式
**逐个展开**（路径是否存在、DROPFILES 头、DropEffect 的值和字节数），
并直接标出哪一项不正常。

### 文件不能往回传：两道独立防线

真机上出现过**无限互传**：从机复制文件 → 主机收到、写剪贴板 → 主机的剪贴板变化
被当成"用户复制了新内容" → 又传回从机 → …… 一次复制就让两台机器不停对传同一个文件，
而且**两边日志全都是正常的**，因为每一步单独看都没错。

治它需要两道**互相独立**的防线，因为它们防的其实是两件不同的事：

**① 时序防线 —— 别把回声发出去。**
写剪贴板的是**一个线程**，而判定"要不要抑制"的是**消息窗口线程**
（`SetClipboardData` 一调用，`WM_CLIPBOARDUPDATE` 就投递出去了）。原来代码是
**写完才**武装抑制，所以通知永远抢在前面。

三道闸门，职责分明：

| 闸门 | 作用 | 依赖时间？ |
|---|---|---|
| `suppress_next()` 大窗口 | 让消息窗口处理通知时直接丢掉，`_pending` 根本不被置位 | 是 |
| **`_writing` 标记** | 写入期间同步循环一律不发布 | **否** |
| `_last_sent_seq` 比对 | 事后兜底 | 否 |

第一道够用最好，**真正的正确性在第二道** —— 不管写的是 1 微秒的
`SetClipboardData` 还是 1 秒的 PowerShell 子进程，行为完全一样。
（一开始只做了第一道，那是**在赌时间**；被指出了才补上第二道。）

**② 语义防线 —— 这个文件本来就是对端的，不该往回传。**
`Staging.is_received(path)` 按**位置**判断：落在暂存区里的文件就是接收下来的。
`publish_local` 在决定要不要发起传输之前先问 `all_from_peer()`，全来自对端就直接跳过。

判据刻意用位置而不是"我记得收过这几个路径"：`_paths` 只活在当前进程、还会被 TTL
清理掉，而"在暂存区里"这个事实跨进程、跨重启都成立。

要求**全部**路径都来自对端而不是"至少一个"：混着本机文件时仍按用户的新复制处理 ——
宁可多传一次，也不要漏掉用户的真实意图。

### 文件续传：靠"名字 + 大小 + mtime"

接收端在 `FILE_BEGIN` 时扫描**整个本对端的暂存区**，找到同名且 size/mtime 一致的
文件就回 `FILE_ACK` 要求跳过。两个细节：

* **必须扫整个暂存区**，不能只看当前传输目录 —— 每次传输 ID 都是新的，
  只看自己的目录等于没有续传；
* **找到之后用硬链接挂到当前传输目录**，而不是直接复用旧路径 —— 旧路径可能
  马上被 TTL 清掉，硬链接既不占空间又把 TTL 时钟重置到当下。

### 文件传输的路径安全

对端发来的文件名**不可信**。`_safe_filename()` 会剥掉所有目录成分、过滤非法字符、
给保留设备名（`CON`/`NUL`/`COM1`…）加前缀。不做这一步就是经典的路径穿越漏洞
（往系统目录写文件）。测试里专门覆盖了 `..\..\windows\system32\evil.dll` 这类输入。

### 文件同步的阈值策略

```toml
auto_transfer_max_mb = 200
over_threshold_action = "ask"    # ask | skip | transfer
```

`ask` 的默认行为是**通知 + 不传**，而不是弹框等待。理由：netclip 是后台常驻的，
没法同步地问用户；默认不传保证"不会突然占满带宽"。想让它无条件传就设 `transfer`。

### 剪贴板竞争：为什么写失败要"整段重来"

实测在剪贴板竞争激烈时（连续读写几十次之后）会出现：
`OpenClipboard()` 成功，紧接着 `EmptyClipboard()` 返回
`ERROR_CLIPBOARD_NOT_OPEN(1418)` —— 剪贴板状态被别的进程在中间动过。

这种情况下继续拿着那个"打开"的句柄毫无意义，所以 `write_formats()` 把
**Open + Empty + 写入**当作一个整体，失败就整段退避重来（约 0.25s 窗口）。
清空和写入必须在**同一个**剪贴板会话里完成：如果清空后先关掉再重新打开，
中间那一瞬间别的进程可以插进来，结果是"我们清空的东西被抢走、写进去的内容
混着别人的"。

这个失败只在"跑完整测试套件"时稳定复现（前面的用例把剪贴板搞热了），
单独跑那一个用例永远正常 —— 定位它花了不少时间，靠的是给失败路径加上
`last_error` 字段，把后台线程里被吞掉的异常暴露到断言消息里。

**读这一侧也有两个瞬时故障**（300 次「写-读」往返实测出来的）：

| 症状 | 概率 | 处理 |
| --- | --- | --- |
| 列出了格式，但每个 `GetClipboardData` 都返回空句柄 | ~2.5% | `capture()` 换个会话重读 |
| 刚写完，读到的却是"一个格式都没有" | ~1% | 同上 |

重开一次会话就正常（实测 3 次全部恢复，其中一次连等待都不需要），所以
`capture()` 会按 `CAPTURE_RETRY_MS` 整次重跑，最多多花 70ms。

**为什么这点小概率值得处理**：空结果是要被丢掉的 —— 剪贴板序号已经推进，
监听器不会再看第二眼，那一次复制就**永远同步不过去**。而 `capture()` 只在
剪贴板真的变了的时候才被调用（不是定时轮询），所以代价可控。

反过来，如果是"被配置过滤 / 超过单格式上限 / 进程内句柄格式"这类**确定**的
原因导致读不出来，就不重试 —— 重试多少次都一样，只会白白拖慢每一次采集。

`write_formats()` 里也补了一条：`EmptyClipboard` 成功、但每一种格式的
`SetClipboardData` 都被抢掉时同样整段重来。那时候剪贴板**已经被我们清空了**，
就此收手等于把用户原来的内容删掉还什么都没换上，比不同步还糟。（只有数据本身
有问题 —— `ValueError` —— 才算确定性失败，不重试。）

### 托盘：为什么不用 pystray

1. 项目定位是"零依赖、复制过去就能跑"，为一个图标引入 pystray + Pillow 不划算；
2. pystray 要求自己的 `run()` 占据主线程消息循环，而我们**已经**有一个主线程
   消息循环，自己写可以直接把托盘窗口挂进去，少一个线程和一个消息泵；
3. 图标自己解析 `.ico`（`extract_icon_frame()`）+ GDI 画出来，不需要 Pillow。

图标本身是 `assets/netclip.ico`（`tools/make_icon.py` 从 PNG 生成，含
16/24/32/48/64/128/256 七档），状态用**外沿那一圈描边**的颜色表达：
灰=等待对端、绿=已连接、橙=光标在对端、红=已暂停。光标在对端是最需要一眼看出来
的状态（用户会疑惑"鼠标怎么不动了"）。

> 为什么是**圈**而不是右下角的状态圆点：右下角正好是脸，而托盘图标只有
> 16×16，盖住那一点就认不出是谁了。圈只压在图片四边的背景上，一点主体都不挡，
> 周长还大得多。

`.ico` 里的每一档都是 PNG 压的（Pillow 11 的行为，实测七档全是），所以
`extract_icon_frame()` 里有一个只用 `zlib` 的手写 PNG 解码器（IDAT + 五种行
过滤器）——**解码**比编码简单得多。BMP 存法的老式 `.ico` 也支持，
另外还处理了 `tRNS`/调色板/灰度，以及"整帧 alpha 全 0 时改用 1 位 AND 掩码"。

图标文件找不到就退回"圆角方块 + 状态色 + 首字母"，功能不受影响。

打包时 `--icon` 和 `--add-data` **都要**：前者把图标塞进 exe 的**资源**里
（资源管理器、任务栏），后者把同一份文件拷进包里 —— 托盘图标要在运行时读出
字节自己解码、再叠描边，光有资源取不到像素。

> GDI 句柄的坑：`CreateCompatibleDC` / `CreateDIBSection` 等返回的是**可能是高地址
> 的句柄**。`ctypes` 的 restype 必须声明成 `c_void_p`，否则会抛
> `OverflowError: int too long to convert` 或静默截断成负数。

### 鼠标抖动的根因：`SetCursorPos` 会产生"真实"的移动事件

这是实现鼠标共享时最容易翻车、又最难从代码上看出来的一点：

`SetCursorPos()`（以及注入的绝对移动）会让系统发出 `WM_MOUSEMOVE`，
而这条事件**不带** `LLMHF_INJECTED` 标志 —— 它走的是正常的光标移动路径。
于是：

```
A 让 B 把光标挪到边缘
  -> B 的光标真的动了，B 的钩子产生一条真实移动事件
  -> B 处于 LOCAL，以为是用户在动鼠标，转发给 A
  -> A 注入位移，A 的光标也动了，A 又转发给 B
  -> ...（无限循环）
```

两边的位移互相咬住，现象就是**"鼠标被吸在一个位置高频抖动、完全推不动"**，
而且因为每次都走的是"真实输入"路径，日志里看不出任何异常。

修法是 `HookThread.ignore_next_move()`：每次我们自己移动光标之后，开一个
60ms 的时间窗，把窗口内的移动事件丢掉（只更新坐标基准，不上报）。
用时间窗而不是数条数，是因为 `SetCursorPos` 到底会产生几条移动事件由系统的
鼠标事件合并策略决定，数条数很容易漏。

`Session._warp_cursor()` 里两件事都要做：`reset_mouse_tracking()`（清坐标基准）
+ `ignore_next_move()`（丢事件）。少任何一个都会抖。

排查工具：`python -m netclip.selftest warpguard`

### 键盘不转发：修饰键的 VK 归一化

配置里写 `alt`，解析出来是 `VK_MENU(0x12)`；而低级键盘钩子上报的是
`VK_LMENU(0xA4)` / `VK_RMENU(0xA5)`。`win` 写的是 `VK_LWIN(0x5B)`，
用户可能按的是右 Win（`VK_RWIN 0x5C`）。**直接用 VK 比会永远不相等。**

后果分两种，都很糟：

* 本机热键（`win+l`、`alt+tab`…）完全失效；
* 更麻烦的是 `_holding_local_hotkey` 会在错误的地方被置位，然后一直拦到
  修饰键松开 —— 用户感觉就是"键盘完全没映射到被控端"。

修法是用 `_normalize_mod()` 把左右修饰键归一到同一个虚拟键再做匹配。
测试里 `test_normalize_mod_maps_left_right_variants` 和
`test_win_hotkey_does_not_swallow_everything` 专门钉住这两条。

另外修饰键状态现在以**事件流**为准（`_track_mods`），只在事件流里还没出现过
修饰键时才回退去问 `GetAsyncKeyState`。这样热键逻辑才是可测的 ——
真实键盘状态看不到单测构造的虚拟按键。

### 键盘排查开关

```toml
[input]
debug_keys = 10    # 启动后打印前 10 次"按键被拦下"的原因
```

会输出类似：

```
按键未转发: vk=0x41 scan=0x1E down=True | 原因: 当前是 LOCAL（光标不在对端） | 模式=local 修饰键=无
```

### REMOTE 状态必须用「统一坐标系」，不能用本机坐标

这是从**真实双机追踪数据**里查出来的最严重的一个设计错误，值得单独写清楚。

现象：推到对端之后，光标像被弹簧拉住 —— 挪走一点就被拽回来，只有动得非常快
才能短暂脱离，然后又会被拉住。

追踪数据显示主机的虚拟光标累积到了 **(-873, -1092)**，而对端屏幕只有
1920×1080 —— **它早就跑到屏幕外了**。两台机器的日志都显示只有一次 `ENTER`、
从机从未接管，所以不是抢控制权，而是主机的「位置认知」坏了。

根因：REMOTE 状态下我沿用了**本机坐标**来表示位置。但

* 本机光标会被**本机屏幕**的边界钳住；
* 而此时用户关心的、以及从机真实所处的，是**对端屏幕**上的位置。

两个坐标系一旦脱节就再也回不来：主机算出来的位置越漂越远，之后每一个判断
（还要不要转发、是否贴边、什么时候交接）都建立在错误基准上。

**修法**：引入「统一坐标系」—— 把两台屏幕并排摆好，本机在 `[0,w)×[0,h)`，
对端紧贴共享边放到外侧，另一条轴按 `alignment` 对齐。

```
本机 1280x800、对端 1920x1080、right + center：
  本机  x ∈ [0, 1280)      y ∈ [0, 800)
  对端  x ∈ [1280, 3200)   y ∈ [-140, 940)
```

REMOTE 期间只维护「统一坐标系里的光标位置」，并且**钳位到对端屏幕**。
这样主机模拟的位置和从机的真实光标永远一致。

踩过的两个附带坑，都写成了断言：

1. **换算必须是纯平移，不能缩放。** 早先版本换算时用了比例，每帧都带一点误差，
   越走越偏。
2. **平移量只取共享轴那一维的尺寸**（`right`/`left` 用 `local.w`，
   `up`/`down` 用 `local.h`），另一条轴保持本机坐标。早先把 `alignment`
   同时用在两条轴上，结果两块屏幕在穿越方向**重叠**，坐标一进去就是负数。
   测试里有一条断言专门检查"两块屏幕不重叠"。

### 回到本机靠「原路推回共享边」，对端的外边界只是普通边界

光标进入对端之后，模型被**钳在对端矩形内**。所以要交回控制权，判定的必须是
**对端屏幕朝向本机的那条边**（也就是进来时的入口边）：

```
主机（对端在下）: 光标顶到对端屏幕顶边 + 继续往上推  -> 交回控制权
从机（对端在上）: 光标顶到对端屏幕底边 + 继续往下推  -> 交回控制权
```

交回之后本机光标正好停在它自己的共享边上（进入时就是冻在那条边上的），位置连贯。
入口点本身就贴着近边，所以加了个"必须离开入口边 32px 以上"的门槛，
免得刚进去的一个抖动就弹回来。

**对端屏幕的「外」边界（离本机最远的那条边）只是它自己的屏幕边界**，
和本机其它三条边一样**只钳位、不做任何切换**。

这里踩过两次，方向正好相反，值得记下来：

1. 早期**只有**"推到外边界就交回控制权"这一条路径（因为原路返回根本没实现，
   而 `layout.detect_return` 虽然写了却从来没被调用过）。用户必须绕到对端屏幕的
   另一头碰一下才能回来 —— "从机的鼠标要从主机顶端才能回到自己"。
2. 补上原路返回之后，那条外边界逻辑就只剩副作用了：**对端屏幕的另一头本来
   就不该能穿过去，却会莫名其妙把控制权跳回来** —— "鼠标移到主机顶端会跳回从机"。

交接那一下必须**立刻停止处理同一批事件里剩下的移动**，否则光标会在交接瞬间
又往前冲一大段（实测冲到屏幕外 600 多像素）。

### 释放残留按键：鼠标按钮绝不能无条件补 UP

交回控制权 / 断线时会释放对端残留的按键，否则"对端还按着 Ctrl"会让之后的点击
全变成 Ctrl+点击。

但**鼠标按钮只能释放"确实按着"的那些**。真机上踩过：`force=True` 时无条件补了一条
`WM_RBUTTONUP`，而资源管理器是**收到 RBUTTONUP 就弹右键菜单**的 ——
用户看到的现象是"鼠标离开从机时莫名其妙点了一下右键"。
单独一条修饰键 UP 没有副作用，所以只有修饰键允许无条件补。

### 本机热键不能配「单个修饰键 + 主键」

`local_hotkeys` 的拦截策略是"**整段拦下**"：某个组合的修饰键一齐全，就进入拦截段，
直到修饰键全部松开为止，中间所有按键都不转发。这是为了让 `ctrl+alt+del` 这种
"主键在最后"的组合也能被完整挡下。

代价是：**`win+l` / `alt+tab` 这类"单个修饰键 + 主键"的组合，会把那个修饰键本身
也吞掉**。配了 `win+l` 之后 Win 键完全传不到对端（Win+E / Win+D / Win+方向全废），
`alt+tab` 同理吞掉 Alt。真机上用户报的就是"Win 键不能映射"。

所以默认只留两个修饰键以上的组合（`ctrl+alt+del`、`ctrl+shift+esc`）；
逃生另有 `hotkey_recapture`，不怕被锁在对端。

### 鼠标位移必须用**绝对定位**发送，不能只发相对位移

这是真机上抓到的、也最反直觉的一个坑。Windows 会把**注入的**相对鼠标位移
再过一遍「提高指针精确度」的加速曲线
（`HKCU\Control Panel\Mouse` 的 `MouseSpeed` / `MouseThreshold1/2`）。
同一台机器上实测（`MouseSpeed=1, MouseSensitivity=10`）：

| 请求位移 | 光标实际走的 |
|---|---|
| 1 px | **0 px**（直接丢失） |
| 5 px | 6 px |
| 20 px | 42 px（2.1x） |
| 80 px | 290 px（3.6x） |

于是"主机算出来的位移"和"从机光标真正走的距离"永远对不上：两端的位置模型从
第一帧起就发散，撞到对端屏幕边缘后被钳住，用户看到的就是**光标被弹簧拉住、
挪走一点又被拽回去**。加速度曲线还是**每台机器各自的用户设置**，所以不可能
靠"两边都调成一样的"来回避。

绝对定位（`SetCursorPos` / `SendInput(MOVE|ABSOLUTE)`）不走这条曲线，
同机实测**误差 0**。因此：

* `MOUSE_MOVE` 帧同时带 `dx/dy`（相对位移，保留给老版本对端）和
  `x/y`（**对端坐标系下的绝对落点**，由主机的统一坐标模型算出）；
* 收到 `x/y` 的一方走绝对定位，收不到才退回相对注入；
* 通道层合并鼠标帧时，`dx/dy` **累加**，`x/y` 取**最后一条** ——
  绝对落点表示"现在应该在哪"，与路径无关，累加是错的。

### 位移的基准必须是「系统光标当前位置」，不是「上一条 pt」

低级鼠标钩子的 `MSLLHOOKSTRUCT.pt` **不是**"光标现在在哪"，而是
**"如果允许这次移动，光标会到哪"**：

```
pt = 光标当前位置 + 本次原始增量
```

于是基准的选择就决定了成败：

* **LOCAL（不吞事件）**：移动会被提交，"当前位置"就是上一条 `pt`，
  所以早期用 `pt - 上一条pt` 在 LOCAL 下一直是对的；
* **REMOTE（吞掉事件）**：移动**不提交**，光标冻在穿越点。这时
  `pt - 上一条pt` 算出来的是

      delta(n) - delta(n-1)     <- 位移的**差**

  人手平滑移动时相邻增量几乎相等，于是转发出去的是 **0**。

真机数据（每秒诊断行）把这个形态完整呈现出来：

```
模式=remote | 移动事件 952 (938/秒) | 钩子pt跨度 227x57 | 光标跨度 0x0 | 转发位移 (-62,22)
```

每秒 900 多条事件、`pt` 跨度 227 像素，**转发出去却只有 ±几十，累计几万条事件的
净位移不到 10 像素**。用户看到的就是"鼠标像被弹簧拉住"。

正确基准是 `pt - 光标当前位置`，它恢复出的正是 `delta(n)` —— 也就是本机光标
"本来会"移动的距离（含系统指针加速），这才是该转发的东西。

`tools/frozen_delta_probe.py` 可以自动化地证实这一点（装一个"吞掉移动"的钩子，
注入已知位移，对比两种基准）：注入 20px 时，相邻差是 `(0,0)`，而
`pt - 光标位置` 是 `(42,0)`。

### 合并窗口内的位移必须**累加**，不能丢

输入通道有一个 8ms 的合并窗口（`network.move_coalesce_ms`），目的是把每秒
上千条移动压成一帧。早期实现在"同键帧已排队"时**直接丢弃新帧**，注释写着
"让 writer 稍后把这段时间累积的位移一次性收走"—— 但那些帧**根本没进队列**，
`_collect_moves` 抽不到任何东西，它变成纯粹的限流器：

```
t=0.000  帧1(dx=5, x=100) 入队
t=0.001  帧2(dx=5, x=105) 丢弃
   ... 8ms 窗口内约 7 帧全丢 ...
t=0.008  writer 取出帧1，队列已空 -> 只发【x=100】
```

**每个窗口只发出"窗口开头那一个位置"。** 更糟的是用户停手的那一刻：
最后一个窗口里的位移永远不会被应用，从机光标就停在旧位置上不动 ——
正是"拉走又被拉回去"。

现在改成往"还躺在队列里的那一帧"上**累加**（`dx/dy` 累加，`x/y` 取最后一条，
因为绝对落点与路径无关）。同一个 key 仍然只有一帧在队列里，不会撑爆队列。

### 穿越交接的 `from` 字段：要告诉对端"它的哪条边被进入"

`ENTER` 里的 `from` 必须是**对端**被进入的那条边，也就是**本机方位的反方向**：
对端在本机右边 -> 本机从自己的右边界出去 -> 落在对端的**左**边界。

早期发的是本机自己的 `peer_position`，于是对端把光标摆到了反方向那条边上。
真机追踪数据（主机在右、对端屏宽 1280）：

```
主机模型期望对端光标落在 (8, 680)      <- 对端左边缘
对端实际把光标摆到     (1271, 686)     <- 对端右边缘
```

差了整整一个屏宽，对端光标从第一帧起就贴在错误的边缘、只能朝一个方向挪
9 像素然后被拉回来。这又是一条独立的"弹簧"来源，和加速度那条互不掩盖。

### 握手必须总是带上真实分辨率

`layout.local_screen` 没配时（默认就是自动探测），早期**什么都不发**，
于是对端一直用配置里的兜底值 `peer_screen`。真机上两台实际是 2048x1152 和
1920x1200，却互相以为对方是 1920x1080 —— 对端矩形算错，钳位边界和
"推到对端外边界就交接"的判定点跟着一起错，而且错得**没有任何日志痕迹**。
现在无论如何都会把系统报的虚拟桌面矩形发过去。

### DPI 感知：不能假设，必须在启动时显式设定

netclip 需要对端知道真实的屏幕尺寸，还要让鼠标钩子的坐标、`GetCursorPos`
和"屏幕边界"落在同一个坐标空间里。而 DPI **不感知**的进程会被 Windows
虚拟化整个坐标系（150% 缩放下 `GetSystemMetrics` 把 1920x1200 报成
1280x800），边界就落到了错误的位置。

但一个进程的 DPI 感知级别由三样东西共同决定，**同一台机器换个启动方式就可能
不一样**：`python.exe` 的清单、兼容性标志
（`HKCU\...\AppCompatFlags\Layers`，真机上 python.exe 被挂过 `~ HIGHDPIAWARE`）、
以及从父进程**继承**。

所以不能猜：`winapi.ensure_dpi_awareness()` 在创建任何窗口之前先读当前级别，
不达标才逐个 API 尝试（PMv2 -> 每显示器 -> 系统），最后读回真实状态写进日志。
启动日志里那两行 `DPI 感知:` 和 `屏幕(进程视角):` 就是排查这类问题的第一现场。

### 坐标空间自查工具

```powershell
python tools/cursor_space_probe.py     # 无需人工操作，全自动
```

它用 `SendInput` 注入**已知**的位移和绝对位置，再对照 `GetCursorPos` 和
鼠标钩子的 `pt`，一次性回答四个问题：

* 相对注入有没有被加速曲线放大（A 组，比例明显偏离 1 就是有）；
* 钩子的坐标和 `GetCursorPos` 是不是同一个空间（A 组的"差"恒为非零定值就是不同）；
* 绝对注入准不准（B 组）；
* **光标能不能推到屏幕四条边**（D 组；推不到就说明有别的程序在钉住光标）。

最后一条尤其重要：真机上遇到过"钩子一直在报 ±1~±8 的位移、但系统光标被钉在
同一个点 30 秒没动过"的情况 —— 只看位移数据完全看不出异常，必须看钩子回报的
**原始坐标**。

### 断线保护

最糟的失败模式不是"不工作"，而是"看起来卡住了"。所以：

- 应用层心跳 2s，超时 6s 判定断线（TCP 自身的 keepalive 在 Windows 上默认要
  2 小时才发第一个探测包，拔网线后根本等不到）
- 处于 REMOTE 但对端不可用 → 立刻把控制权收回本机
- 收回时释放所有鼠标按钮和修饰键，否则"对端还按着 Ctrl"会让本机点击全部变成
  Ctrl+点击

## 清理暂存文件

平时**不需要手动清**：`deliver = "clipboard"` 时文件先落在

```
%LOCALAPPDATA%\netclip\staging\<名字>\<传输ID>\<文件名>
```

netclip 自己有个 `netclip-staging-cleanup` 线程，每 `max(60s, TTL/4)` 扫一次
（默认 TTL 120 分钟 → 每 30 分钟），删掉 mtime 超过 TTL 的传输目录。
只要 netclip 一直在跑，占用就是"最近两小时收过的文件"，有界。

想立刻清一次就**双击 `clean.bat`**：它会先列出要删的东西和大小，探一下 netclip
在不在跑（在跑会警告"正在传输的会失败、剪贴板里的会失效"），确认后删除并报告释放了多少。

**它不碰 `Downloads\netclip`** —— 那是交付给你的文件，不是暂存。

两个已知的小缺口（长期运行的话都碰不到，所以没修）：

* **启动时不扫**，第一次清理要等满一个间隔（30 分钟）—— `while not stop.wait(interval)`
  是先等再清。上次异常退出留下的东西要等一会儿才轮到。
* **netclip 不在跑就没人清** —— 关机期间积累的不会被回收。
* 暂存目录那一层的名字用的是**本机**设备名而不是对端名（`factory.py` 传的是
  `cfg.device.resolved_name()`），跟 `Staging` 的文档不一致。改名之后旧目录不会再被扫到。

## 打包成 exe

原来的部署方式是"把整个目录复制到另一台机器"，那里面有源码、测试、脚本上百个文件。

```powershell
python tools/build_exe.py            # 默认：目录版 dist\netclip\（27 个文件，13.8 MB）
python tools/build_exe.py --onefile  # 单文件版 dist\netclip.exe（6.8 MB，见下面取舍）
```

**目标机器不需要装 Python** —— 整个 CPython 运行时（`python310.dll`、标准库、
`VCRUNTIME140.dll`）都打进包里了。验证方式：把 PATH 砍到只剩
`C:\Windows\System32`（`Get-Command python` 找不到），exe 照跑，
`--selftest env` 还会报出内置的那个 Python 版本。

**部署到另一台机器：**

```powershell
netclip.exe --gen-config     # 第一次：生成 config.toml（写在 exe 旁边）
# 改 config.toml 里的 peer_ip / peer_position / psk
netclip.exe --check          # 校验
netclip.exe                  # 启动（托盘图标照常）
netclip.exe --selftest keys --seconds 8    # 自检也进了 exe
```

**开机自启**在 exe 场景下更简单 —— 计划任务的操作直接填：

| | |
|---|---|
| 程序 | `C:\...\netclip\netclip.exe` |
| 起始于 | `C:\...\netclip`（exe 所在目录） |
| 勾选 | **使用最高权限运行**、**只在用户登录时运行** |

不需要 `start.ps1` / `netclip_task.vbs` 那套脚本了。

### 为什么默认是**目录版**而不是单文件

`--onefile` 每次启动都要把自己解压到 `%TEMP%\_MEIxxxxxx`（约 **11.8 MB**）。
正常退出会清掉，但**被强杀不会** —— 而 netclip 恰恰经常被强杀
（`start.bat` 的第 3/4 项就是 `Stop-Process -Force`）。真机上实测堆了 **6 个，70.9 MB**，
而且悄无声息。

更麻烦的是：**正在运行的那个实例依赖它的 `_MEI` 目录** —— 清理系统临时文件时
很容易当成垃圾误删掉它。真机上就误删过一次（删到一半被文件占用挡住，进程勉强活着，
但之后任何一次延迟导入都可能失败）。

目录版没有这些问题：

| | `--onedir`（默认） | `--onefile` |
|---|---|---|
| 复制 | 1 个文件夹，27 个文件，13.8 MB | 1 个文件，6.8 MB |
| 启动 | 快 | 慢 1~2 秒（每次自解压） |
| 临时目录 | **完全没有** | 每次约 11.8 MB，强杀会残留 |

27 个文件的文件夹比源码树（几百个文件）已经少得多，拖过去一次就好。

### 几个刻意的设计

**控制台保留（不加 `--noconsole`）。** `--check` / `--dump-formats` / 全部自检
都要输出，砍掉控制台这些就全瞎了。**"不弹窗"是启动方式的事，不是 exe 的事** ——
计划任务里勾"只在用户登录时运行"不会弹窗；自己写脚本启动就用
`Start-Process -WindowStyle Hidden`。

**`config.toml` 绝不打进包，`config.example.toml` 一定打进包。** 前者每台机器
不一样、用户要手改，必须在 exe 旁边（`config.app_dir()`）；后者是程序自带的只读
资源（`config.resource_path()`）。

这两个概念**必须分开**：打包后 `__file__` 指向解包目录（onefile 下每次启动还是
**新的**一个），拿它去找 `config.toml`，用户改的配置永远读不到，日志还会散落在
temp 里越堆越多。真机上就是这么踩的，测试在 `tests/test_packaging.py`。

**`--noupx`。** UPX 压过的 exe 更容易被杀毒软件误报，而 netclip 要常驻运行 ——
被拦一次很难查。省那点体积不值得。

> 另外提醒：PyInstaller 打出来的 exe **可能被杀毒软件误报**（这是打包器的通病，
> 不是这个项目特有的）。真遇到了就把 `dist` 目录加进白名单。

## 测试

```powershell
python -m tests.run            # 全部
python -m tests.run layout     # 只跑名字里含 layout 的模块
```

测试文件兼容 pytest，所以装了 pytest 的话 `pytest tests/` 也能跑。
`test_win_clipboard.py` 会临时改写剪贴板内容（结束时还原），
所以跑测试时不要同时复制重要内容。

**不会**写会移动鼠标或注入按键的自动化测试 —— 那会干扰正常使用。
这类验证交给 `python -m netclip.selftest` 手动跑。

### `test_wiring.py`：静态一致性检查

这套源码是从会话记录里恢复出来的，恢复过程留下过一批"读起来没问题、跑起来才炸"
的损伤（比如一个类的形参被删了但调用点还在传、一个函数被同名旧版本静默覆盖）。
这类问题**没法靠单测发现** —— 有的要真的装全局钩子才会跑到，有的要等用户真的
复制一个文件过来。所以 `test_wiring.py` 不执行代码，只做静态检查：

| 检查 | 挡住的真实故障 |
|---|---|
| `self.x` 被读、本类却从未赋值 | `HookThread.__init__() got an unexpected keyword argument 'chain'` |
| 调用点传了目标类不接受的关键字 | 同上（同一个 bug 的另一半） |
| 模块顶层重名定义 | `build_file_clipboard_items` 被旧版本覆盖，生效的是会崩的那份 |
| 引用了未定义的模块级名字 | `NameError: name 'SHELL_IDLIST_FORMAT' is not defined` |

名字相关的两条用标准库的 `symtable` / `ast` 实现，实测整套代码零误报。
加新代码后如果这几条红了，**先看是不是真的有两份定义或写错了名字**，不要急着改测试。

## 已知限制

- **任务管理器等「提权窗口」收不到转发的输入**（鼠标移上去就像"卡住"）。
  这是 Windows UIPI（用户界面特权隔离）的**系统限制**，不是本程序的缺陷：未提权的
  进程，其低级钩子（`WH_MOUSE_LL` / `WH_KEYBOARD_LL`）和 `SendInput` 对**高完整性
  级别**的窗口（任务管理器、注册表编辑器、安装程序……）一律无效 —— 钩子会被系统
  **静默屏蔽**，netclip 连事件都收不到，所以看起来是"卡住"而不是"没反应"。
  Deskflow 有完全相同的 issue
  （[#8611](https://github.com/deskflow/deskflow/issues/8611)），
  [Synergy 官方文档](https://help.symless.com/hc/en-us/articles/35742001220369-How-to-make-Synergy-work-with-UAC-prompts)
  也专门讲这个，QQ 远程桌面同样如此。

  **解法**：让 netclip 本身提权运行（高完整性 → 低完整性是允许的）。
  用 `start.bat` **第 10 项**以管理员身份重启，或用**第 9 项**安装【最高权限】自启
  （登录时由系统直接提权启动，不弹 UAC，日常最省事）。
  启动日志里会有一行 `权限级别:` 直接告诉你当前是哪种，不用猜。

- **只支持 Windows**（大量直接使用 Win32 API）
- **只支持两台机器、单显示器**。多显示器场景下 `local_screen` 需要手动填写
  虚拟桌面坐标，穿越判定可能不准。
- **不支持跨屏拖拽文件**（OLE 拖放太复杂）。跨屏传文件走"复制粘贴"路径。
- 局域网内**内容不加密**，只有握手用 PSK 做认证防止串台。
- 剪贴板里的"延迟渲染"格式（数据由源程序在粘贴时才生成）无法转发。
- 部分带绝对路径或指向外部数据源的格式（Excel 数据透视缓存、`Link Source`）
  跨机必然失效。
